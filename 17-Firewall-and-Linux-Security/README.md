# 1. What Is a Firewall?

A **firewall** controls network traffic according to defined rules or policies.

On a Linux host, a firewall can inspect traffic entering, leaving, or passing through the system.

```text
                Linux Host
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
    INPUT        OUTPUT        FORWARD
       │            │            │
       └────────────┼────────────┘
                    ▼
               Firewall
                    │
                    ▼
             Allow / Drop / Reject
```

A firewall is one layer of defense. It does not replace:

- authentication
- patching
- endpoint protection
- least privilege
- secure configuration
- application security
- monitoring

---

# 2. Why Host Firewalls Matter

Imagine a Linux server running:

```text
SSH       :22
Web       :443
Database  :3306
Monitoring service
Internal API
```

Even if an application is listening, the host firewall can restrict who can reach it.

```text
Remote Host
     │
     ▼
Network
     │
     ▼
Linux Firewall
     │
     ├── allowed → service
     │
     └── blocked → dropped/rejected
```

This supports **defense in depth**.

---

# 3. Netfilter — The Linux Kernel Framework

Linux provides packet-filtering functionality through the kernel's **Netfilter** framework.

A simplified model is:

```text
Network packet
      │
      ▼
Linux networking stack
      │
      ▼
Netfilter hooks
      │
      ├── filtering
      ├── NAT
      └── connection tracking / other processing
      │
      ▼
Decision
```

Netfilter is the underlying kernel framework; user-space tools such as nftables interact with it.

---

# 4. nftables

**nftables** is the modern Linux packet-filtering framework and command-line toolset.

Basic command:

```bash
sudo nft list ruleset
```

This displays the active nftables ruleset when nftables is in use.

Conceptually:

```text
nftables
   │
   ├── tables
   │     └── chains
   │            └── rules
   │
   └── packet-processing policy
```

Modern Linux firewall administration increasingly uses nftables directly or through higher-level tools.

---

# 5. Tables, Chains, and Rules

Think of nftables like this:

```text
TABLE
 │
 ├── CHAIN
 │     ├── RULE
 │     ├── RULE
 │     └── RULE
 │
 └── CHAIN
       ├── RULE
       └── RULE
```

A **table** organizes firewall objects.

A **chain** contains rules evaluated for packets at a particular hook/context.

A **rule** describes a match and an action.

Example conceptual rule:

```text
IF protocol = tcp AND destination port = 22
THEN allow
```

---

# 6. INPUT, OUTPUT, FORWARD

These are fundamental packet-flow concepts.

## INPUT

Traffic destined for the local host.

```text
Network → Linux Host
             ↑
           INPUT
```

## OUTPUT

Traffic generated by the local host.

```text
Linux Host → Network
      ↑
    OUTPUT
```

## FORWARD

Traffic passing through the Linux host toward another destination.

```text
Network A → Linux Router → Network B
                 │
              FORWARD
```

A normal workstation/server may mainly care about INPUT and OUTPUT. A Linux router/firewall also needs FORWARD.

---

# 7. ACCEPT, DROP, REJECT

Firewall rules commonly produce decisions such as:

### ACCEPT

Allow the packet to continue.

### DROP

Silently discard the packet.

```text
Packet → DROP → no normal response from firewall
```

### REJECT

Discard the packet and actively send an appropriate rejection response where supported.

```text
Packet → REJECT → explicit failure response
```

### Security distinction

DROP and REJECT have different network behavior. The appropriate choice depends on the service, troubleshooting requirements, threat model, and policy.

---

# 8. Stateful Firewalling

Modern firewalls often track connection state.

Common conceptual states include:

```text
NEW
ESTABLISHED
RELATED
INVALID
```

Example:

```text
Client → Server
       NEW
        │
        ▼
   connection tracked
        │
        ▼
  ESTABLISHED traffic
```

A stateful firewall can allow return traffic for an established connection without writing a separate rule for every packet direction.

---

# 9. Connection Tracking

Linux can track network flows using connection-tracking facilities.

Conceptually:

```text
Source IP:port
      +
Destination IP:port
      +
Protocol
      │
      ▼
Connection state
```

This helps firewalls make decisions based on whether traffic belongs to an existing flow.

For diagnostics, systems may provide tools such as:

```bash
sudo conntrack -L
```

if the `conntrack` utility is installed.

---

# 10. iptables — Legacy but Important

You will still encounter:

```bash
iptables
```

in older systems, scripts, documentation, and interviews.

Traditional iptables concepts include:

```text
Tables
  ↓
Chains
  ↓
Rules
```

Common built-in chains include:

```text
INPUT
OUTPUT
FORWARD
```

### Important modern detail

On many modern distributions, an `iptables` command may be implemented through a compatibility layer backed by nftables.

Therefore:

```text
iptables command
      ≠ always
old kernel firewall implementation
```

Learn the concepts, but prefer the firewall framework actually used by your distribution.

---

# 11. Inspect iptables Rules

If iptables is being used:

```bash
sudo iptables -L -n -v
```

Useful information includes:

- chain
- policy
- source
- destination
- protocol
- port
- packet counters
- byte counters

These counters can help determine whether rules are matching traffic.

---

# 12. UFW

**UFW — Uncomplicated Firewall** provides a simpler interface for firewall administration, especially on Ubuntu-based systems.

Status:

```bash
sudo ufw status verbose
```

Enable:

```bash
sudo ufw enable
```

Disable:

```bash
sudo ufw disable
```

> ⚠️ If you are connected over SSH, enabling a restrictive firewall without first allowing your SSH access can disconnect you.

---

# 13. UFW Rules

Allow SSH:

```bash
sudo ufw allow 22/tcp
```

Allow HTTPS:

```bash
sudo ufw allow 443/tcp
```

Deny a port:

```bash
sudo ufw deny 23/tcp
```

View numbered rules:

```bash
sudo ufw status numbered
```

Delete a rule by number when appropriate:

```bash
sudo ufw delete NUMBER
```

Always inspect the current rules before modifying them.

---

# 14. UFW Application Profiles

UFW can use application profiles on systems that provide them.

List profiles:

```bash
sudo ufw app list
```

View a profile:

```bash
sudo ufw app info "OpenSSH"
```

Then an administrator may allow an application profile rather than manually specifying every port.

The exact available profiles depend on installed packages.

---

# 15. Default UFW Policies

A common restrictive model is:

```text
Incoming → deny by default
Outgoing → allow by default
```

But the correct policy depends on the host's role and organization's requirements.

Inspect:

```bash
sudo ufw status verbose
```

### Security principle

Start with the business/service requirement:

```text
What must communicate?
       ↓
Who needs access?
       ↓
From where?
       ↓
To which port/service?
       ↓
Allow only that traffic
```

---

# 16. firewalld

**firewalld** is widely used in Red Hat-family and other Linux environments.

Check status:

```bash
sudo firewall-cmd --state
```

Get active zones:

```bash
sudo firewall-cmd --get-active-zones
```

List current configuration:

```bash
sudo firewall-cmd --list-all
```

List all zones:

```bash
sudo firewall-cmd --get-zones
```

---

# 17. firewalld Zones

A zone represents a trust/policy context for interfaces or sources.

Conceptually:

```text
Network Interface
       │
       ▼
     Zone
       │
       ├── services
       ├── ports
       └── firewall policy
```

Common zone names include:

```text
public
internal
trusted
home
work
```

The available zones and their defaults depend on the system.

### Security idea

Different network contexts may require different policies.

---

# 18. firewalld Services and Ports

List allowed services:

```bash
sudo firewall-cmd --list-services
```

List explicitly allowed ports:

```bash
sudo firewall-cmd --list-ports
```

Allow HTTPS permanently in the active/default configuration as appropriate:

```bash
sudo firewall-cmd --permanent --add-service=https
```

Then reload:

```bash
sudo firewall-cmd --reload
```

### Important

The exact active zone matters. Do not assume that a command changes every interface's policy.

---

# 19. Runtime vs Permanent firewalld Configuration

firewalld commonly distinguishes runtime and permanent configuration.

```text
Runtime
  ↓
Current active policy

Permanent
  ↓
Configuration intended to survive reload/restart
```

A common workflow is:

```bash
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --reload
```

Then verify:

```bash
sudo firewall-cmd --list-all
```

This is another example of:

```text
Runtime state ≠ persistent configuration
```

---

# 20. Firewall vs Listening Service

These are different concepts.

A service may listen:

```text
0.0.0.0:8080
```

while the firewall blocks external access.

Conversely, a firewall may allow TCP/8080 while no process listens there.

Therefore:

```text
Listening port
      +
Firewall policy
      +
Network routing
      +
Service behavior
      ↓
Actual reachability
```

For host audits, always inspect both the service and firewall.

---

# 21. Firewall Rule Ordering

Rules may be evaluated in a defined order.

Conceptually:

```text
Packet
  │
  ▼
Rule 1 → match? → action
  │
  no
  ▼
Rule 2 → match? → action
  │
  no
  ▼
Rule 3
```

A broad rule placed before a more specific rule can change the result.

This is a common troubleshooting mistake.

---

# 22. Default Policy

A firewall must have behavior when no specific rule matches.

Conceptually:

```text
Specific rules
      │
      ▼
No match?
      │
      ▼
Default policy
```

A secure server commonly uses a restrictive inbound policy, but the correct design depends on its function.

Do not copy a generic policy to a production host without understanding required traffic.

---

# 23. Source and Destination Filtering

A rule can consider:

- source IP
- destination IP
- source port
- destination port
- protocol
- interface
- connection state
- other packet metadata

Example concept:

```text
Allow TCP
from 10.10.10.0/24
   to port 22
```

This is more precise than:

```text
Allow TCP/22 from anywhere
```

### Principle

**Restrict the source whenever the service does not need global access.**

---

# 24. Interface-Based Filtering

A host can have multiple interfaces:

```text
eth0 → Internet
eth1 → Internal network
```

Firewall policy can differentiate traffic by interface.

```text
Internet interface
      ↓
restrictive policy

Internal interface
      ↓
internal policy
```

This is useful for servers with separate management/data networks.

---

# 25. IPv4 vs IPv6 Firewall Rules

A common mistake is securing IPv4 while forgetting IPv6.

Check IPv6 addresses:

```bash
ip -6 addr
```

Check IPv6 routes:

```bash
ip -6 route
```

Then understand how your firewall handles IPv6.

### Security principle

If IPv6 is active, include it in the host's security review.

Do not assume:

```text
IPv4 firewall policy = IPv6 firewall policy
```

---

# 26. Firewall Logging

Logging can help answer:

```text
What traffic was blocked?
When?
From where?
To where?
Which protocol/port?
```

But logging everything can create huge volumes.

Good logging should be:

- intentional
- useful
- rate-controlled where appropriate
- sent to monitoring/SIEM infrastructure when required

---

# 27. Kernel and Firewall Logs

Inspect kernel messages:

```bash
journalctl -k
```

Search for firewall-related messages:

```bash
journalctl -k | grep -Ei 'nft|iptables|firewall|drop|reject'
```

Exact log formats depend on the firewall and logging configuration.

### SOC relevance

Firewall logs can provide network telemetry even when the application itself does not log the blocked connection.

---

# 28. Firewall Troubleshooting Workflow

When traffic is unexpectedly blocked:

```text
Client
  │
  ▼
DNS correct?
  │
  ▼
Route correct?
  │
  ▼
Destination reachable?
  │
  ▼
Service listening?
  │
  ▼
Firewall rule matches?
  │
  ▼
Default policy?
  │
  ▼
Firewall logs?
```

Commands:

```bash
ip route get DESTINATION
sudo ss -lntup
sudo nft list ruleset
sudo ufw status verbose
sudo firewall-cmd --list-all
journalctl -k
```

Use only the commands relevant to the firewall framework actually installed.

---

# 29. `nft monitor trace`

For advanced nftables troubleshooting, nftables can provide packet tracing in suitable configurations.

One commonly encountered command is:

```bash
sudo nft monitor trace
```

This can help an administrator understand how packets traverse nftables rules.

### Caution

Tracing can generate substantial output on a busy system. Use it carefully and preferably in a controlled lab when learning.

---

# 30. Firewall Security Design

A good host firewall policy starts from required services.

Example web server:

```text
Internet
   │
   ├── HTTPS 443 → ALLOW
   │
   └── SSH 22 → only trusted admin sources

Everything else inbound
   ↓
BLOCK unless required
```

This is the principle of **least network privilege**.

---

# 31. Management Plane vs Data Plane

A useful architecture is to separate management access from application traffic.

```text
Management Network
       │
       └── SSH

Application Network
       │
       ├── HTTPS
       └── API
```

Firewall policy can restrict administrative access to management networks.

This reduces exposure of sensitive administration interfaces.

---

# 32. Firewall and SSH

Suppose SSH is required only from a management subnet:

```text
10.20.0.0/24 → TCP/22 → ALLOW
Everything else → TCP/22 → BLOCK
```

This is stronger than exposing SSH globally when global exposure is unnecessary.

Combine:

```text
Firewall
+
SSH keys
+
least privilege
+
monitoring
```

for defense in depth.

---

# 33. Firewall and Web Services

For a web server, you might need:

```text
TCP 443 → public
TCP 80  → redirect/required policy
TCP 22  → management only
Database port → internal only
```

Do not expose database ports simply because the application needs them internally.

Use network segmentation and source restrictions where appropriate.

---

# 34. Host Firewall Does Not Stop Everything

A firewall cannot by itself prevent:

- malicious local processes
- attacks through allowed ports
- application vulnerabilities
- stolen credentials
- malicious authenticated users
- data theft over legitimate protocols
- local privilege escalation

Therefore:

```text
Firewall
   +
Authentication
   +
Least privilege
   +
Patching
   +
EDR/monitoring
   +
Logging
   +
Secure applications
```

forms a stronger defense.

---

# 35. Firewall Changes as Security Events

Unexpected firewall changes can be important SOC signals.

Examples:

```text
New inbound port allowed
Default policy changed
SSH access widened
Firewall disabled
Unexpected NAT rule
Unexpected forwarding rule
Logging disabled
```

An analyst should correlate the change with:

- administrator activity
- change ticket
- deployment
- package update
- automation
- configuration management
- incident response activity

# 36. SOC Scenario — Firewall Disabled

### Alert

Monitoring reports that the host firewall is no longer active.

### Step 1 — Identify framework

```bash
systemctl status nftables
systemctl status firewalld
sudo ufw status
```

Not all commands/services will exist on every host.

### Step 2 — Determine actual state

```bash
sudo nft list ruleset
```

and, where applicable:

```bash
sudo firewall-cmd --state
```

or:

```bash
sudo ufw status verbose
```

### Step 3 — Determine who/what changed it

Correlate:

```text
Time
 ↓
Administrator login
 ↓
Configuration change
 ↓
Process/service activity
 ↓
Change-management record
```

### Step 4 — Assess exposure

Inspect:

```bash
sudo ss -lntup
```

Ask which services became reachable.

# 37. SOC Scenario — Unexpected Port Allowed

Suppose monitoring detects a new firewall rule allowing TCP/4444.

Do not immediately delete it.

Investigate:

```bash
sudo nft list ruleset
sudo ss -lntup
```

Then identify:

```text
Rule
 ↓
Port
 ↓
Process listening?
 ↓
User
 ↓
Executable
 ↓
Service
 ↓
Change source
 ↓
Expected?
```

If suspicious, preserve relevant evidence and follow the organization's containment process.

---

# 38. SOC Scenario — Allowed Traffic but Service Unreachable

Suppose firewall rules appear to allow TCP/443.

Still check:

```bash
sudo ss -lntp | grep ':443'
```

If nothing is listening, the firewall is not the problem.

Then check:

```bash
systemctl status SERVICE
journalctl -u SERVICE
```

This demonstrates:

```text
Firewall allowed
   ≠
Application available
```

---

# 39. SOC Scenario — Unexpected Outbound Rule

An outbound firewall rule allows a new destination range.

Investigate:

```text
Who created it?
Why?
When?
Which process needs it?
Which destinations are included?
Is the range broader than necessary?
```

Correlate with:

```bash
sudo ss -antp
```

and system logs/change records.

Avoid automatically removing a rule that could be part of legitimate service operation.

For a Linux server, document:

# 🔥 Troubleshooting Scenarios

## Scenario 1 — SSH Suddenly Stops Working

If you are still connected:

```bash
sudo ss -lntp | grep ':22'
```

Then inspect firewall state.

Check:

```bash
sudo nft list ruleset
```

or the active UFW/firewalld configuration.

### Important

Never close your only working SSH session while testing firewall changes remotely.

---

## Scenario 2 — Service Listening but Remote Client Cannot Connect

Check:

```bash
sudo ss -lntup
```

Then:

```bash
sudo nft list ruleset
```

Then inspect routing:

```bash
ip route
```

Then application logs.

---

## Scenario 3 — Firewall Rule Exists but Traffic Still Blocked

Possible reasons:

- wrong chain
- wrong interface
- wrong source/destination
- IPv4 vs IPv6 mismatch
- rule ordering
- earlier rule drops traffic
- wrong active firewalld zone
- application is not listening
- upstream firewall blocks traffic

Use counters/tracing/logs where appropriate.

---

## Scenario 4 — Traffic Allowed but Connection Still Fails

Remember:

```text
Firewall
   ↓
only one layer
```

Check:

```bash
sudo ss -lntp
ip route
ip neigh
```

Then test the application itself.

---

## Scenario 5 — Firewall Configuration Changed After Reboot

Check the difference between:

```text
runtime configuration
```

and:

```text
persistent configuration
```

For firewalld, inspect runtime/permanent configuration appropriately.

For nftables/UFW, determine how the distribution loads rules at boot.

```text
     ▼
Source IP / Port
     │
     ▼
Destination IP / Port
     │
     ▼
Firewall Decision
     │
 ┌───┴────┐
 ▼        ▼

 ▼        ▼

 ▼
Process
 │
 ▼
User / Service

 ▼
Expected?

 ▼
Investigate / Correlate
```

> "Port 4444 was allowed."

Ask:

> **Who changed the rule, why was it changed, what process needs the access, who can reach it, and what happened before and after the change?**

# 🧩 Linux Security Beyond the Firewall

A secure Linux host should be approached as multiple layers:

```text
                    LINUX SECURITY
                          │
      ┌───────────────────┼───────────────────┐
      ▼                   ▼                   ▼
 Authentication       Authorization        Network
      │                   │                   │
 SSH keys              permissions         firewall
 passwords             ACLs                segmentation
      │                   │                   │
      └───────────────────┼───────────────────┘
                          ▼
                    Processes/Services
                          │
                          ▼
                       Logging
                          │
                          ▼
                       Monitoring
                          │
                          ▼
                    Patch Management
                          │
                          ▼
                       Hardening
```

The firewall is one important layer, not the entire security model.
